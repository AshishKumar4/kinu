## Scope

Frozen to three arms before the run, by decision, not by measurement:
`snapshot-chain` (incumbent), `bounded-layers` and `merkle-pack`
(challengers). `r2fs` and `overlay-cas` retired from the decision because both
are red-structural on cells 6.10 (racing containers) and 6.17 (two containers,
one head): a format that cannot meet a durability cell by its architecture is
not a candidate for the default. The driver carries the freeze as
`DECISIVE_ARMS` in `scripts/bench-devbox-strategies.ts`; the retired arms stay
readable as historical artifacts and their conformance rows remain.

## Admission

The run-level verdict (`G0`-`G9`) is written by the driver when the last arm
settles and is appended below with the teardown listing. From the settled
rows: the incumbent completed its lifecycle proof and every priced cell; both
challengers failed their lifecycle proof (`merkle-pack` at the wake,
`bounded-layers` at the first decisive checkpoint) and therefore cannot be
ranked. A run in which no challenger completes cannot displace the default,
whatever the incumbent's own numbers.

## Recommendation

Keep `snapshot-chain` as the default. It is the only arm that completed the
lifecycle proof and every decisive cell on 2026-09-05: wake 7932 ms with 2
remote operations on a 71 MB base, 64 MiB quiesce 9585 ms, all four security
cells refused, the fault cut left the record identical. Its two open
structural reds (6.14, 6.15: a delta the size of the changed inode, 89478808
B for a 4 KiB write into a 64 MiB file) are the cost of the format and are
stated, not hidden; a challenger that meets them has to complete a run first.

`DEFAULT_DEVBOX_STRATEGY` in `packages/devbox/src/storage.ts` names this
decision; `Devbox` returns it and `KinuSandbox` states it explicitly.

## The challengers' live failures, root-caused (2026-09-05, after the run)

Three defects behind the two refusals above, each fixed at the source on
this tree; the decisive run has NOT been repeated yet, so the rows above
stand and the recommendation stands with them until it is.

- `merkle-pack` wake: the deployed arm runs the v1 candidate runner, and its
  reader fetched one authenticated range per packed chunk. A file chunks at
  the 4 KiB target, a FUSE-mounted store answers one range per round trip,
  and the 75,265,384 B tree was ~18,000 reads sixteen at a time: 300 s. The
  builder lays a file's chunks out contiguously, so the reader now coalesces
  a slice's distinct extents into one read per pack run and holds every
  chunk inside a run to its own digest (`coalescePackRuns`, `readRun` on the
  reader seam, shared with the v2 view). Measured in `merkle-pack.test.ts` on
  2026-09-05: a 96 MiB dense tree restored in 11,000-24,000 reads before and
  in fewer than 320 after (one per 512 KiB slice plus one per node and the
  index), the same 88-112 MiB of bytes; a 100 MiB window over a sparse file
  cost 1,025 reads before and fewer than 16 after. The receipt's
  `totalRemoteOps` and `payloadBytes` are the object and byte counts the
  wake states.
- `merkle-pack` release after the failure: the attach was classified
  terminal with the abandoned restore still running in the container, and
  the stop's final checkpoint then waited on that container past the 120 s
  release deadline. A box whose restoration is `unattached` admitted no
  caller and restarted no process, so `quiesce` now skips the checkpoint and
  the detach and stops the container, answering `skipped: nothing is
  attached to commit`. Regression: `lifecycle-generation.test.ts`, red
  before (the stop ran a checkpoint) and green after.
- `bounded-layers` closure proof: the envelope names mount-relative keys
  (`obj/<sha>`, `closure/<sha>`), the product's own verification joins them
  to the payload prefix, and the fixture's facts asked the bucket for the
  bare keys, so all 146 read absent. The facts join the prefix and report
  the joined key; the objects were there. Regression:
  `tests/workerd/candidate-closure-facts.test.ts`, red before, green after.

Cell 6.14 for `merkle-pack` names a second thing: the conformance battery's
`merkle-pack` column runs the v2 sidecar arm (`merklePackV2Arm`), while the
deployed arm runs the v1 runner, so the battery's green on 6.12-6.15 does
not measure the codec the decisive run measures. The live 6.14 failure is
the read granularity above, and its fix is the same mechanism.

Not done on this tree, stated rather than implied: the `bounded-layers`
publish path is still one object at a time through the mount, each written
to a temporary name, renamed and read back for its digest (four store
operations per object; 516 s for the 64 MiB quiesce, and no decisive
checkpoint settling in 25 min), and cells 6.12 and 6.15 still refuse on the
512 KiB fixed-grid chunking and the per-generation closure listing; the
dirty-window re-chunk with fixed-size metadata is the fix both need. The
battery has no cell recording restore and backup time against tree size at
three sizes; the ladder records checkpoint time per change size only. The
decisive rerun, its admission per gate and the teardown listing follow the
next run.
