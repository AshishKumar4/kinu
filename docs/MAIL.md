# Mail in Kinu: design note (draft for review, 2026-10-19)

The owner asked (2026-10-19) for mail in Kinu, with Mailflare as the model for the mailbox:

- the deploying user gets their own address (ashish@kinu.run);
- every workspace and every agent gets an address, and its agents can see or listen to it;
- mail.<domain> opens a Gmail-like mailbox, and a mail icon sits in the app;
- the whole thing is integrated with Kinu and "AI native".

This note covers the design, with the gallery wireframe (`?frame=mail`) and the DDL (§11) for review. Nothing is built before that.

Sources, read-only:

- Kinu: next-rc 16931690e. Scouts' reports are cited by file:line in their transcripts.
- Mailflare: ea91c3f06, cloned at /mnt/local/kinu/ref/mailflare.
- Cloudflare's Email Service docs, fetched 2026-10-19.
- DNS measured with `dig @1.1.1.1` on 2026-10-19.

## 0. What exists, what the platform can do, and what was measured

**Kinu already has a "Mission Inbox"**, but it is not a mailbox:

- **Routing:** `<workspace-name>@EMAIL_DOMAIN` reaches the workspace's root agent (`cf/src/email/handler.ts:19`).
- **Who may write:** the owner, plus an allowlist, may send a message that becomes an event and wakes a turn. The turn's final text is mailed back on the thread (`core/src/events/ingress/email.ts`, `cf/src/email/outbound.ts`).
- **What it drops:** attachments are discarded and nothing is kept as mail. There is no user or agent address, no compose, and no UI.
- **It has never run:** kinu.run has no MX record (measured below).

**What the platform gives (Cloudflare Email Service):**

- **Email Routing (inbound).** Free on every plan, inbound unlimited.
  - It routes by rule to a Worker's `email()` handler. A catch-all is possible on the apex domain only; subdomains take literal rules, at most 200 per domain.
  - Plus addressing (`user+tag`) is supported once enabled, and `message.to` keeps the tag.
  - Inbound messages are limited to 25 MiB.
  - Mail that fails both SPF and DKIM is rejected, and so is mail that fails the sender's DMARC policy.
- **Email Sending (outbound).** Public beta since 2026-04-16, Workers Paid only.
  - 3,000 messages a month are included, then $0.35 per 1,000.
  - Onboarding a domain adds `cf-bounce` MX and SPF records, DKIM at `cf-bounce._domainkey` (d = the domain, so it aligns), and `_dmarc`.
  - Per message: at most 5 MiB, 50 recipients and 32 attachments.
  - `Message-ID` is generated by the platform. `In-Reply-To` and `References` may be set, so threading works.
  - Delivered, bounced, complained and rejected events can be subscribed to through Queues.
  - `send_email` bindings can restrict senders only to a fixed list. That cannot express "this agent may send only as itself", so Kinu's code is the boundary.

**Measured on 2026-10-19:**

- **kinu.run has no mail DNS.** No MX, no `_dmarc`, no `cf-bounce`, no DKIM; its only TXT record is an OAuth publisher tag.
- **mail.kinu.run is already taken by preview routing.** It resolves through the `*.kinu.run` Worker route and answers with Kinu's JSON 404, because the preview-suffix catch-all claims it (`core/src/preview/preview-origin.ts:75`).
- **Big mail providers publish `p=none`.** `_dmarc.gmail.com`, `_dmarc.outlook.com` and the owner's own `_dmarc.ashishkumarsingh.com` are all `p=none`; yahoo.com is `p=reject`.

**Security finding in today's code.** The Mission Inbox treats a message as the owner's when the envelope `MAIL FROM` equals the owner's email (`core/src/events/ingress/email.ts:133`).

- For an owner at a `p=none` domain, someone else can send with `MAIL FROM` set to the owner's address and sign DKIM for their own domain. That passes the edge's "SPF or DKIM" rule, and `p=none` means nothing is rejected.
- The message then wakes the agent as the owner.
- It is not live, since no deployment is onboarded. The new router fixes it (§4); a live test proves the fix once a domain is onboarded.

**Mailflare** is Next.js 16 on OpenNext with D1, R2 and Queues, React 19 + Tailwind 4 + shadcn, about 14k lines of UI.

- It has real MIME handling, attachments in R2, a split view, compose with autosaved drafts, stars, snooze, folders, and websocket updates.
- It has no conversation threading (it stores `threadId = Message-ID`), no full-text search, no AI, and no SPF/DKIM/DMARC evaluation.
- **Provenance:** AshishKumar4/mailflare began on 2026-09-03 as a "source repo import" by cloudflare[bot], a Deploy-to-Cloudflare clone of hieunc229/mailflare (its README credits @hieuSSR). The owner has one commit on top. The owner is therefore not its only author, and cannot relicense it. It is AGPL-3.0-or-later.
- **So Kinu copies none of it:** no code, styles or assets. Mailflare is a product reference for behaviour and UX only (§7).

## 1. Addresses

There is one mail domain per deployment, `EMAIL_DOMAIN`, and every address sits on its apex. Email Routing's catch-all exists only on the apex, so one catch-all routes all mail to the Kinu Worker.

| Who | Address | Example |
|---|---|---|
| A person | `<username>@D` | `ashish@kinu.run` |
| A workspace | `<workspace>.<username>@D` | `research.ashish@kinu.run` |
| An agent | `<agent>.<workspace>.<username>@D` | `scout.research.ashish@kinu.run` |
| Any of them + tag | `…+<tag>@D` | `ashish+receipts@kinu.run`: delivered to the same box, the tag kept as a label |

**Labels and how they are read:**

- **Labels contain no dots,** so an address is read right to left: the last label is the person, then the workspace, then the agent. There are at most 3 labels.
- **Each label is at most 20 characters.** The whole local part fits RFC 5321's 64 octets.
- **Username:** `[a-z0-9]([a-z0-9-]{0,18}[a-z0-9])?`. It is claimed once, globally, and reserved words cannot be claimed (postmaster, abuse, admin, noreply, mail, ops, dmarc, security, support, root…).
- **Workspace label:** the workspace's name lowercased, with `.` and `_` turned into `-`, then cut to 20 characters. It is unique per person; a clash gets `-2`.
- **Agent label:** the agent's name. It is bound to the agent's id, never to its name: a released name is never given to a new agent, because the old address stays retired.

**What a person sees:** a person's own box holds their mail, and the boxes of their workspaces and agents appear beside it. The Mail app shows them all (§7).

**Self-hosted deployments** use the same scheme on their own domain (`me@their.domain`). Their owner may also claim short top-level aliases for any of their boxes, such as `hello@their.domain` delivered to a workspace. kinu.run does not allow this, so that names cannot be squatted.

**The Mission Inbox form `<workspace>@D` retires.** No deployment ever received mail through it: kinu.run has no MX, and self-hosting needs a manual onboarding that the docs record as not done. If a self-host turns out to have onboarded, a one-time import keeps its workspace addresses as aliases.

**Who gets an address (the owner, 2026-10-19):** the deployment's owner gets their username address, with their workspaces' and agents' addresses under it. Other accounts get none until the owner turns on the deployment setting `mail.accounts` ("Other accounts may claim an address"). It is off by default, on kinu.run and on every self-host.

## 2. Where mail lives and who owns it

**The account owns its mail:** its person, workspace and agent boxes alike. That gives one unified index, one search and one quota.

**`MailName` Durable Object, one per username** (`idFromName(label)`):

- It holds `{ user_id, state }`. Naming the object is the global lock, so the first claim wins.
- Inbound lookup is one hop, with no singleton on the hot path.
- A rename claims a new name pointing at the same account. The old name stays as an alias for a grace period and is never given to someone else.

**`Mailbox` Durable Object, one per account** (`idFromName(user_id)`). It holds:

- the account's addresses (person, workspaces, agents), and who may wake or send as each;
- every message's metadata, threads, labels and read state;
- a full-text index (DO SQLite supports FTS5);
- the send outbox and its delivery status.

**Bodies, raw `.eml` files and attachments go to a new R2 bucket, `MAIL`,** under `mail/<user_id>/…` and addressed by content hash.

- Metadata rows stay small. The 2 MB row limit and the shared 10 GB per-DO limit matter for mail.
- The R2 object holds the bytes; the Mailbox holds the fact that the account received them.
- Counts (unread, per box) are queries over rows, never kept beside them.

**Why not the alternatives:**

- **Not the UserDO:** it is the account's control object, and mail volume and search would load it.
- **Not the workspace DO:** a person's box exists without any workspace, and a unified inbox across many workspace DOs would mean fanning out every list and search.

**Workspace and agent DOs don't hold mail.** They hold the agent's event (§4), and the agent reads its box through the Mailbox.

**Retention:**

- Trash is purged after 30 days.
- A workspace that is deleted retires its addresses. Its mail stays in the account's box, under the archived workspace, until the owner purges it.
- There is no storage quota (the owner, 2026-10-19).

## 3. What agents get: one codemode namespace and events, no new native tool

**A `mail` namespace** (`native: false`, declared once as Operations in the shared catalog):

| Member | Impact | What |
|---|---|---|
| `mail.address()` | observe | the actor's own address, and its workspace's |
| `mail.find({ box?, query?, unread?, from?, label?, before?, limit? })` | observe | thread summaries, newest first |
| `mail.read(threadOrMessageId)` | observe | messages with text bodies and attachment metadata, marked untrusted (§4) |
| `mail.draft({ to, cc?, subject, text, replyTo?, attach? })` | effect, no approval | a draft in the box, shown to the owner in Mail |
| `mail.send(draftIdOrMessage)` | effect, approval | sends as the actor's own address (rules below) |
| `mail.update(id, { read?, starred?, labels?, archived? })` | effect, own box only | |

**What an agent can read:**

- Its own box, and its workspace's.
- The person's own box only from a workspace the owner has explicitly granted ("this workspace may read my mail"). That is a step-up setting, and it is what the triage assistant uses (§8).

**Who may send as which address** (enforced in the Mailbox DO against the authenticated caller):

| Address | Who may send as it |
|---|---|
| Agent address | that agent, and the person |
| Workspace address | the workspace's root agent, and the person |
| Person's address | only the person: from the Mail UI, or by approving an agent's draft, where approving is the person pressing Send |

**`mail.send` approval:**

- **What is approved:** exactly the bytes sent (from, recipients, subject, body hash, attachment hashes), as a new approval kind `mail-send`, modelled on `slate-effect`. It is shown in the Work tab's decision stack, and inline in Mail as "scout wants to send this".
- **Standing approvals,** each scoped to one recipient or one thread: "Always for replies on this thread" or "Always to alice@…".
- **No approval needed:** replies to the verified owner.

**Both backends:**

- The CLI serves the same namespace by proxying to the account's cloud Mailbox when it is signed in.
- Otherwise the namespace is unavailable, with a recorded divergence for `capability-parity`.

## 4. How an agent "listens", and the security model

**Delivery path:**

1. Email Routing's catch-all calls the Worker's `email()`.
2. The Worker reads the address and drops the `+tag` for routing. It finds the username's `MailName` and gets the account.
3. **An unknown username is rejected with SMTP 550.** Usernames are public, and a reject tells the sender.
4. **An unknown workspace or agent label under a known person is accepted** into their "Unknown address" view, so senders cannot enumerate workspace names.
5. The Worker stores the raw message and attachments in R2, parses it with `postal-mime` (Cloudflare's documented parser, and what Kinu and Mailflare already use), and calls `Mailbox.deliver`.
6. `deliver` is idempotent per Message-ID and content hash.

**Is a sender verified?** That is Kinu's own verdict, not the edge's:

- **Verified** means a DMARC pass aligned with the `From` domain. It is read from the top `Authentication-Results` header that Cloudflare's MX adds.
- That header reaches the raw message but not `message.headers` (Cloudflare community report, 2024), so the Worker reads it from the raw header block.
- Only the topmost such header, carrying Cloudflare's authserv-id, counts. Headers a sender added further down are ignored.
- Cloudflare's exact authserv-id and result format are unknown until a domain is onboarded. **Step zero of the build measures them with real mail from gmail.com, outlook.com and yahoo.com.**
- Without a verified pass, the message is unverified.
- **The owner** is a verified message whose `From` address equals the account's email. This replaces today's envelope match.
- **Unverified mail** never wakes an agent and never matches an allowlist. It files to an "Unverified" view; it is not dropped, so nothing real is lost.

**Waking:**

- Delivery to a workspace or agent address calls that workspace DO's `mailArrived(actorId, …)`. That publishes an `email` event into the actor's existing EventLog, which wakes the actor, gets drained, and opens a turn. There is no second turn loop.
- **Each address has a wake policy:**
  - `owner` (the default): only the verified owner wakes it;
  - `allowlist`;
  - `verified`: anyone verified;
  - `never`: store only.
- The existing 30-per-minute gate and the per-actor batching apply.
- Mail that does not wake an agent appears in that agent's context as counts (§8). It is never mailed back automatically.

**Prompt injection:**

- **Mail bodies never reach a prompt's system sections.**
- **The wake's event text carries metadata only:** the verified flag, the sender and the subject. It is escaped (as now) and fenced as untrusted mail. Bodies come only through `mail.read`, whose result says `untrusted: true`.
- **A turn woken by anyone but the verified owner runs in plan mode** (`WorkMode 'plan'`). It may read and draft, and any effect waits for the owner.
- **Today's "reply with the turn's answer" stays for the verified owner only.** That is the Mission Inbox feature.

**HTML and images:**

- HTML is shown only in an empty-sandbox iframe with `default-src 'none'`, the precedent being `FileViewer`'s sealed document.
- Remote images are blocked by default, because they work as tracking pixels. "Show images from this sender" loads them for one sender, through Kinu's own image proxy so the sender never sees the reader's address.
- Agents only ever get the text part.

**Sending limits:**

- **Daily cap per account (the owner, 2026-10-19):** none for the deployment owner's account; 100 a day for any other account, once `mail.accounts` lets it claim an address. Agents' sends count toward their account's cap.
- **Per message:** at most 50 recipients and 5 MiB, the platform's limits.
- **Delivery status:** a Queues subscription feeds bounced, complained and rejected events into each message's status.
- **Automatic pause:** an account whose complaint rate passes 0.1% stops sending until the owner looks.

## 5. Deliverability and DNS

**For kinu.run** (these are the owner's actions in the Cloudflare dashboard, or through the API with their token):

1. **Email Routing on kinu.run:** MX `route{1,2,3}.mx.cloudflare.net` plus the routing SPF TXT. A catch-all rule sends everything to Worker `kinu`, and plus addressing is turned on.
2. **Email Sending for kinu.run:** the `cf-bounce` MX and SPF records, and DKIM at `cf-bounce._domainkey`, signed `d=kinu.run`, which aligns with `@kinu.run`. This needs Workers Paid.
3. **DMARC at `_dmarc.kinu.run`:** start at `v=DMARC1; p=none; rua=mailto:dmarc@kinu.run`, with reports landing in an ops box. Move to `quarantine`, then `reject`, after 2–4 clean weeks of reports.
4. **Staging:** `staging.kinu.run` is a subdomain, so it gets literal routing rules only (no catch-all). It uses a fixed set of eval addresses.

**Onboarding is a deploy step, the same on kinu.run and on a self-host:**

- The step uses the Cloudflare API when the deploy's token has the email permissions: it enables Routing, adds the catch-all rule to the Worker, turns on plus addressing, onboards Sending, and writes `_dmarc` if absent.
- When the token lacks a permission, the step asks the owner: it names the exact dashboard action, or the token scope to add, and waits.
- **`gate:infra` then measures the result:** it queries MX, SPF, the DKIM selector and DMARC over DNS-over-HTTPS, and checks a live round trip.
- That replaces today's check, which passes on any rule line that mentions the Worker and proves no DNS (`scripts/infra-cloudflare.ts:1208`).
- **Plan limits:** the Workers Free plan can receive mail but can send only to verified addresses. The step says so.

## 7. The Mail app, the icon, and mail.<domain>

**In the app:**

- A `/mail` route is added to the app's routes, with a Mail entry in `PRIMARY_NAV` (envelope icon). It shows a count of unread mail that needs you.
- Each workspace view gets an Inbox place listing its own box and its agents' boxes.

**Layout:**

- On desktop, there are three columns:
  - **Places column** (as in Drive): All inboxes; Me; each workspace with its agents nested under it; Needs review (agents' drafts and send asks); Starred; Sent; Drafts; Unverified; Trash.
  - **Thread list.**
  - **Reading pane.**
- On phone, the columns stack.

**mail.<domain> is a permanent redirect to `https://<domain>/mail`.**

- **Why not a separate origin:** the app's session cookie is `__Host-kinu_session`. It is host-only on purpose: no `Domain` attribute, so no other host under the zone can read or set it. A mailbox served on `mail.<domain>` would need a second session for the same person on a second origin, minted through a ticket exchange like the preview viewer pass, with its own sign-out, CSRF boundary (the app accepts writes only from its own origin) and CSP. That doubles the account's attack surface for an address-bar difference.
- **What the redirect gives:** one session, one CSRF boundary and one CSP. A link to `mail.<domain>/<thread>` keeps its path and lands on the same thread in the app.
- **The one change it needs:** `mail.` must be matched before the preview-suffix catch-all, which takes `mail.kinu.run` today (measured: it answers Kinu's JSON 404). No preview or share host label may ever be `mail`.

**Built from scratch on Kinu's own components:**

- Mail is written new, on Kinu's own pieces: `.p-row` text, the Drive's places column, `TileMenu`, `Modal`, `FilledButton`, the shared `Composer`, and `sandboxedHtml` for sealed HTML. It looks and behaves like the rest of Kinu.
- **Mailflare is a product reference only,** for behaviour and UX: what a Gmail-like box offers (a split view, compose with autosaved drafts, stars, attachments with previews, reply quoting, bulk actions). **No Mailflare code, styles or assets are copied** (provenance in §0).
- **What Kinu has that Mailflare lacks:** conversation threads (`In-Reply-To`/`References`), FTS5 search, labels rather than a single folder, sender verification, and agents' boxes.
- The wireframe (`packages/cf-backend/src/gallery-mail.tsx`) is written this way: Kinu components only, with fixtures.

## 8. "AI native", concretely

1. **Every agent's inbox is in its context.**
   - A dynamic-context section reads, for example: "Mail: 3 unread in your box (2 from verified senders), oldest 2h. From: …, subjects: …". It shows counts, verified flags and escaped subjects; no bodies.
   - It changes only when the box changes, like the other volatile sections.
2. **Triage.**
   - The owner can name one workspace their mail assistant. It is granted read access to their box and wakes on new mail in batches, with a cost budget.
   - It labels threads (Needs you / FYI / Newsletters / Can wait) and writes a one-line summary per thread, which shows in the list. It drafts replies.
   - It sends nothing as the person.
3. **Drafting in the reading pane.** "Draft a reply" asks the assistant and puts the draft in the composer. "Summarise" works the same way. The person edits and sends.
4. **Mail into work.** "Send to workspace…" on a thread hands it to a chosen workspace as a task, with the owner's authority, because the owner clicked it.
5. **Provenance everywhere.**
   - Sent mail shows who wrote it ("sent by scout · research").
   - An agent's send ask shows the exact message with Approve / Edit / Deny, both in Mail and in the decision stack.
   - The approval spends once.

## 9. What is measured before the build, and how it is proven

Mail ships as one feature: every part of this note together, the Mission Inbox's ingress replaced in the same change (its path deleted; one path, which requires a DMARC-aligned `From`).

**Measured first:**

- FTS5 `MATCH` with long queries, in workerd. A DO's SQLite refused a long LIKE before.
- Once kinu.run is onboarded: Cloudflare's `Authentication-Results` format, from real gmail.com, outlook.com and yahoo.com mail.

**Proven:**

- The usual gates: tests red then green, mutations, a whole Armada tier, and a review.
- Live rows on the first deploy that carries mail:
  - a round trip to a person, a workspace and an agent;
  - a forged owner message is refused its wake;
  - an agent's send waits for approval.

## 10. Decisions

**Main decided, 2026-10-19:**

- The new router replaces the old ingress in the same change, with a DMARC-aligned `From` required. No separate patch to the old path.
- No phases. `mail.<domain>` is the permanent redirect (§7).
- Domain onboarding is a deploy step: the API where the token allows, the owner asked otherwise (§5).
- Mailflare is a product reference only: Kinu copies none of its code, styles or assets, and builds Mail from scratch on its own components (§0, §7).

**The owner decided, 2026-10-19:**

- Addresses: only the deployment's owner has one, with their workspaces' and agents'. Other accounts need the owner's setting `mail.accounts` (§1).
- Send cap: none for the owner's account; 100 a day for any other (§4).
- No storage quota; Trash empties after 30 days (§2).

## 11. DDL (for review before any build)

There are two new Durable Object classes, each with its own schema class: `mailname` and `mailbox`. Every number the UI shows is a query over these rows; none is stored beside them.

### `MailName`: one per root label (`idFromName(label)`)

Its single row is the claim. Naming the object is the global lock.

```sql
CREATE TABLE IF NOT EXISTS mail_name (
  label        TEXT    PRIMARY KEY CHECK (length(label) BETWEEN 1 AND 20),  -- the object's own name; its form is checked in code
  user_id      TEXT    NOT NULL,                                            -- the account whose Mailbox it routes to
  kind         TEXT    NOT NULL CHECK (kind IN ('username', 'alias')),
  target_path  TEXT,                                                        -- an alias's box (see mail_addresses.path); NULL for a username
  state        TEXT    NOT NULL DEFAULT 'active' CHECK (state IN ('active', 'former', 'retired')),
  claimed_at   INTEGER NOT NULL,
  ended_at     INTEGER,
  CHECK ((kind = 'alias') = (target_path IS NOT NULL)),
  CHECK ((state = 'active') = (ended_at IS NULL))
);
```

**States:**

- **`active`:** the label routes mail.
- **`former`:** a username the account renamed away from. It still routes to the same account, and is never claimable by anyone else.
- **`retired`:** nothing routes there, and the label is never reissued.

**Who may claim:**

- The deployment's operator (`CONTROL_PLANE_ADMINS`) may always claim.
- Any other account may claim only while the site setting `mail.accounts` is on. It is off by default.

### `Mailbox`: one per account (`idFromName(user_id)`)

```sql
-- The account's mail identity: its address and the username it reads under.
CREATE TABLE IF NOT EXISTS mail_box (
  id          INTEGER PRIMARY KEY CHECK (id = 1),
  user_id     TEXT    NOT NULL,
  email       TEXT    NOT NULL,           -- the account's sign-in email: a verified message From it is the owner's
  username    TEXT    NOT NULL,           -- the account's current label; MailName holds the claim, this is its pointer back
  created_at  INTEGER NOT NULL
);

-- Every box of the account. A path is relative to the username: '' is the person, 'research' a workspace,
-- 'scout.research' an agent. A rename touches no row here.
CREATE TABLE IF NOT EXISTS mail_addresses (
  path        TEXT    PRIMARY KEY CHECK (length(path) <= 41),
  kind        TEXT    NOT NULL CHECK (kind IN ('person', 'workspace', 'agent')),
  workspace   TEXT,                       -- the workspace's name (its Durable Object's), for workspace and agent boxes
  actor_id    TEXT,                       -- the agent the box belongs to; the workspace's root agent for a workspace box
  wake        TEXT    NOT NULL DEFAULT 'owner' CHECK (wake IN ('owner', 'allowlist', 'verified', 'never')),
  reads_person INTEGER NOT NULL DEFAULT 0 CHECK (reads_person IN (0, 1)),  -- a workspace the owner granted their own box (the mail assistant)
  state       TEXT    NOT NULL DEFAULT 'active' CHECK (state IN ('active', 'retired')),
  created_at  INTEGER NOT NULL,
  retired_at  INTEGER,
  CHECK ((kind = 'person') = (path = '')),
  CHECK ((kind = 'person') = (workspace IS NULL AND actor_id IS NULL)),
  CHECK (reads_person = 0 OR kind = 'workspace'),
  CHECK ((state = 'retired') = (retired_at IS NOT NULL))
);

CREATE UNIQUE INDEX IF NOT EXISTS mail_addresses_actor ON mail_addresses (workspace, actor_id) WHERE actor_id IS NOT NULL;

-- Senders who may wake a box whose wake is 'allowlist'. The verified owner always may.
CREATE TABLE IF NOT EXISTS mail_allow (
  path        TEXT    NOT NULL REFERENCES mail_addresses (path),
  sender      TEXT    NOT NULL,           -- canonical lowercase address
  added_at    INTEGER NOT NULL,
  PRIMARY KEY (path, sender)
);

-- A conversation, in the box it arrived in or was started from.
CREATE TABLE IF NOT EXISTS mail_threads (
  id          TEXT    PRIMARY KEY,
  path        TEXT    NOT NULL REFERENCES mail_addresses (path),
  subject     TEXT    NOT NULL,
  folder      TEXT    NOT NULL DEFAULT 'inbox' CHECK (folder IN ('inbox', 'archive', 'unverified', 'trash')),
  starred     INTEGER NOT NULL DEFAULT 0 CHECK (starred IN (0, 1)),
  trashed_at  INTEGER,                    -- emptied 30 days after
  triage      TEXT    CHECK (triage IS NULL OR triage IN ('needs', 'fyi', 'news', 'later')),
  summary     TEXT,                       -- the mail assistant's line
  summarized_by TEXT,                     -- the assistant workspace that wrote it
  created_at  INTEGER NOT NULL,
  CHECK ((folder = 'trash') = (trashed_at IS NOT NULL)),
  CHECK ((summary IS NULL) = (summarized_by IS NULL))
);

CREATE INDEX IF NOT EXISTS mail_threads_box ON mail_threads (path, folder);
CREATE INDEX IF NOT EXISTS mail_threads_trashed ON mail_threads (trashed_at) WHERE trashed_at IS NOT NULL;

-- One message, as received or written. Large parts and the raw message live in R2 under the account.
CREATE TABLE IF NOT EXISTS mail_messages (
  id          TEXT    PRIMARY KEY,
  thread_id   TEXT    NOT NULL REFERENCES mail_threads (id),
  direction   TEXT    NOT NULL CHECK (direction IN ('in', 'out')),
  header_id   TEXT,                       -- Message-ID: the sender's (in), or the platform's once sent (out)
  in_reply_to TEXT,
  refs        TEXT    NOT NULL DEFAULT '[]',  -- References, a JSON array bounded to the 998-octet header line
  from_addr   TEXT    NOT NULL,
  from_name   TEXT,
  to_json     TEXT    NOT NULL DEFAULT '[]',
  cc_json     TEXT    NOT NULL DEFAULT '[]',
  delivered_to TEXT,                      -- the envelope address it reached, with any +tag (in)
  subject     TEXT    NOT NULL,
  at          INTEGER NOT NULL,           -- received (in) or written (out)
  verdict     TEXT    NOT NULL CHECK (verdict IN ('verified', 'unverified', 'ours')),
  auth        TEXT,                       -- the Authentication-Results it was judged by, as received
  snippet     TEXT    NOT NULL DEFAULT '',
  text_body   TEXT,                       -- the text part inline up to 64 KiB, else NULL and text_key set
  text_key    TEXT,
  html_key    TEXT,
  raw_key     TEXT,                       -- the raw .eml (in)
  size        INTEGER NOT NULL,
  read        INTEGER NOT NULL DEFAULT 0 CHECK (read IN (0, 1)),
  written_by  TEXT,                       -- the agent that wrote it (out)
  send_state  TEXT    CHECK (send_state IS NULL OR send_state IN ('draft', 'approval', 'queued', 'sent', 'delivered', 'bounced', 'failed', 'complained')),
  send_digest TEXT,                       -- the hash of exactly what an approval allows to go
  CHECK ((direction = 'in') = (send_state IS NULL)),
  CHECK (direction = 'out' OR (raw_key IS NOT NULL AND written_by IS NULL)),
  CHECK (text_body IS NULL OR text_key IS NULL),
  CHECK ((send_state = 'approval') = (send_digest IS NOT NULL AND written_by IS NOT NULL)),
  UNIQUE (thread_id, header_id)
);

CREATE INDEX IF NOT EXISTS mail_messages_thread ON mail_messages (thread_id, at);
CREATE INDEX IF NOT EXISTS mail_messages_header ON mail_messages (header_id) WHERE header_id IS NOT NULL;
CREATE INDEX IF NOT EXISTS mail_messages_sent ON mail_messages (direction, at);
CREATE INDEX IF NOT EXISTS mail_messages_waiting ON mail_messages (send_state) WHERE send_state IN ('draft', 'approval');

-- Labels on a thread: the person's, the assistant's, and each +tag mail arrived with.
CREATE TABLE IF NOT EXISTS mail_labels (
  thread_id   TEXT    NOT NULL REFERENCES mail_threads (id),
  label       TEXT    NOT NULL CHECK (length(label) BETWEEN 1 AND 40),
  PRIMARY KEY (thread_id, label)
);

CREATE INDEX IF NOT EXISTS mail_labels_label ON mail_labels (label);

-- A file a message carries; its bytes are content-addressed under the account in R2.
CREATE TABLE IF NOT EXISTS mail_attachments (
  id          TEXT    PRIMARY KEY,
  message_id  TEXT    NOT NULL REFERENCES mail_messages (id),
  filename    TEXT    NOT NULL,
  content_type TEXT   NOT NULL,
  size        INTEGER NOT NULL,
  digest      TEXT    NOT NULL,           -- sha256: the R2 key is mail/<user_id>/att/<digest>
  inline_cid  TEXT                        -- Content-ID of an inline part
);

CREATE INDEX IF NOT EXISTS mail_attachments_message ON mail_attachments (message_id);
CREATE INDEX IF NOT EXISTS mail_attachments_digest ON mail_attachments (digest);

-- Search: regenerable from the messages and their R2 parts; rowid is mail_messages' rowid.
CREATE VIRTUAL TABLE IF NOT EXISTS mail_fts USING fts5 (
  subject, sender, body, content = '', contentless_delete = 1, tokenize = 'unicode61 remove_diacritics 2'
);
```

**Outbound sends** use Nimbus's existing outbox (`outbox_mail`), keyed per message id: written before the send, retried with backoff, and dead-lettered after 8 attempts.

### The site setting

The control plane gets one new table, `control` class:

```sql
CREATE TABLE IF NOT EXISTS cp_settings (
  key         TEXT    PRIMARY KEY CHECK (key IN ('mail.accounts')),
  value       TEXT    NOT NULL,
  updated_at  INTEGER NOT NULL,
  updated_by  TEXT    NOT NULL            -- the operator's email
);
```

`mail.accounts` = `'on'` lets accounts other than the operator claim an address, and sets their send cap at 100 a day.

### What changes in existing schema

- **`triggers.kind` loses `'email_route'`.** The allowlist moves to `mail_allow`. No deployment holds such rows, because none was ever onboarded. If any exist, the rebuild drops them; the tables plan shows it.
- **`reply_channels` (`'email_thread'`) stays.** It carries the turn's answer back to the verified owner.

### R2 bucket `MAIL`

All keys sit under `mail/<user_id>/`:

| Prefix | Holds |
|---|---|
| `raw/<sha256>.eml` | raw messages |
| `text/<sha256>.txt` and `html/<sha256>.html` | large text parts, and HTML parts |
| `att/<sha256>` | attachments |

An object goes when the last row naming its digest goes.

### Measured before build

- `fts5` with `contentless_delete` in workerd's SQLite. It needs SQLite 3.43 or later.
- `MATCH` with long queries.
